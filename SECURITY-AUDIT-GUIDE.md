# IAS2 Employee Portal Security Audit Guide

This prototype uses fake data and exists only to demonstrate security controls for the IAS2 project.

## Demonstration accounts

- Employee: `employee@example.test`
- Administrator: `admin@example.test`
- Password for both: `DemoPassword!2026`

Change or remove these accounts before any real deployment.

## Start the prototype

1. Run `php artisan migrate:fresh --seed`.
2. Run `npm run build`.
3. Run `php artisan serve`.
4. Open `http://127.0.0.1:8000`.

Local HTTP is acceptable for local development. HTTPS must be configured and tested on the final deployment environment.

## Audit tests and screenshot evidence

### AUD-01: Account lockout and Multi-Factor Authentication (MFA)

1. **Lockout Test**: Enter an incorrect password five times for `employee@example.test`, then try the correct password. The next attempt must be rejected temporarily. Capture the throttling message.
2. **MFA Challenge Test**: Submit valid credentials (`employee@example.test` / `DemoPassword!2026`). The portal must redirect to `/mfa-challenge` rather than directly to `/dashboard`.
3. **Invalid Code Test**: Enter an invalid 6-digit code (e.g. `000000`). Confirm the error: *"The provided verification code is invalid or has expired"* and verify the `auth.mfa.failed` audit entry.
4. **Valid Code Test**: Enter the active 6-digit TOTP code generated by Google Authenticator (or use the on-screen Demo Helper Auto-Fill). Confirm successful sign-in into `/dashboard` and verify the `auth.mfa.succeeded` audit entry.

### AUD-02: Role-based access control

Sign in as the employee and manually open `/admin/employees`. The server must return a 403 response. Then sign in as the administrator and confirm that the page opens. Capture both results.

### AUD-03: Secure session termination

Sign in and leave the application inactive for 15 minutes. The application must sign the user out, redirect to login, and create an `auth.session.expired` audit entry containing the user and configured idle duration. Also test manual logout and confirm that reopening `/dashboard` requires authentication.

### AUD-04: Audit logging

Sign in as the administrator, edit a dummy employee record, and open `/admin/audit-logs`. Confirm that the log identifies the administrator, action, time, subject record, and IP address. Verify recorded authentication entries (`auth.mfa.challenged`, `auth.mfa.succeeded`, `auth.login.succeeded`, `employee_record.updated`).

## Automated verification

Run `php artisan test --filter=SecurityControlsTest`. These tests independently verify role restrictions, login throttling, MFA challenge redirection, invalid MFA rejection, valid MFA verification, logout invalidation, and audit-log creation.

## Production note

For a public deployment, enable HTTPS at the web server or hosting platform, set `APP_ENV=production`, set `APP_DEBUG=false`, set `SESSION_SECURE_COOKIE=true`, replace demonstration passwords, and restrict access to authorized users.
